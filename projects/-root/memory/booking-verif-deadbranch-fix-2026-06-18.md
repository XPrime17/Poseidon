Scott reported (2026-06-18): StCath staff had no 06/26 tour in their calendar, and he'd stopped getting the tour-booking-verification emails he used to get. Two **separate unwired branches**, same class as [[skyvern-deadbranch-fix]]:

**1) Booking Verification workflow `dUEa8NI0z8vq2LSL`** (Gmail-trigger `subject:Tour Notification New Task/Tour`, polls every min). The `Row Found` IF false-branch (`$json.found != true`) was wired to **nothing**, and a purpose-built Gmail node **`no row`** ("Booking Verification Skipped (Inbound - No Lead Record)", →Scott) sat **orphaned**. Every recent booking is **inbound** → no matching outbound MasterSheet lead row → `Get row(s) in sheet`=`{}` → halted silently, emailed nobody. That's why Scott's verification emails dried up (they only ever fired for OUTBOUND leads that matched the MasterSheet). **Fix:** wired `Row Found`[false] → `no row`, set its `emailType=text`. NOTE the verification workflow still only *truly verifies* outbound bookings (matches AI-captured vs CRM); inbound just gets a "skipped, no action" FYI.

**2) Inbound EOC `3oV7SpPKWmr3xJlQ`** ("Inbound End Of Call - Multicentre"). The `Booking Result` switch (v3.2) only routed `body.status`==`completed`/`failed`, no fallback → dropped. **Fix:** `options.fallbackOutput="extra"` + new Gmail node **`Email: Booking Needs Manual`** (→`centre_email`, BCC Scott per [[feedback-bcc-scott-on-centre-emails]]).

**2b) THE REAL ROOT CAUSE (Scott caught this) — Wait timeout too short.** Both EOC `Wait` nodes (`Wait on Skyvern` inbound, `Wait on Skyvern Webhook1` outbound `4p1V0wESn3kZySt6`) had `resume:webhook, limitWaitTime:15min`. Skyvern's `dispatchWorkflow` passes `webhookCallbackUrl={{$execution.resumeUrl}}` and Skyvern DOES call back with `body.status` ∈ {completed,failed,timed_out,terminated} (proven: outbound `Switch1` routes all 4). But Skyvern browser bookings take **~20 min** (StCath: call 21:39 → LineLeader notif 21:59), so the **n8n Wait timed out at 15 min and resumed with `body=null`** — no status, matches no rule. So the switch-fallback was a band-aid; the booking actually completed, n8n just stopped waiting too early. The LineLeader notification means **StCath 06/26 almost certainly DID book** — staff likely have it. **Fix (`deploy-skyvern-wait-timeout-2026-06-18.py`, backups `*-20260618b.json`):** both Wait nodes 15→**30 min**; outbound `Switch1` had `options={}` (NO fallback) → same latent silent-drop bug → added `fallbackOutput=extra` → existing `Send Manual Booking Needed`. Lesson: a null `body` from a Wait-webhook node = **n8n timeout**, distinct from Skyvern's own `timed_out` status; always give the Wait > the tool's real runtime AND a fallback.

Deploy script `/root/deploy-deadbranch-fix-2026-06-18.py`; backups `/root/backup-bookingverif-20260618.json` + `/root/backup-inbound-eoc-20260618.json`. PipelineRegressionCheck = PASS.
